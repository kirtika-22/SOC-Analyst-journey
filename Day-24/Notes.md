# Day 24 - SOC L1 Incident Response Workflow

## What is Incident Response (IR)?

Incident Response (IR) is a structured process used by SOC teams to detect, analyze, contain, eradicate, recover, and learn from cybersecurity incidents.

### Objectives
- Minimize business impact
- Reduce recovery time
- Prevent future incidents

---

# SOC Levels

## L1 Analyst (Monitoring & Triage)

Responsibilities:
- Monitor security alerts
- Perform alert triage
- Validate alerts
- Categorize incidents
- Escalate to L2/L3
- Document findings

> L1 is responsible for detecting incidents quickly and escalating accurately.

---

## L2 Analyst (Investigation & Analysis)

Responsibilities:
- Deep investigation
- Log correlation
- Root Cause Analysis (RCA)
- Threat analysis

---

## L3 Analyst (Threat Hunting & Incident Response)

Responsibilities:
- Malware analysis
- Threat hunting
- Incident containment
- Recovery
- Detection engineering

---

# Incident Response Lifecycle (NIST SP 800-61)

1. Preparation
2. Detection & Analysis
3. Containment
4. Eradication
5. Recovery
6. Post-Incident Review

---

# 1. Preparation

Purpose:
Prepare people, tools, and processes before an incident occurs.

Activities:
- Create Incident Response policies
- Configure SIEM detection rules
- Deploy Wazuh agents
- Configure EDR
- Train analysts
- Create IR playbooks
- Define communication plans

---

# 2. Detection & Analysis

Purpose:
Identify suspicious activity and determine whether it is a real security incident.

Common Data Sources

- SIEM (Wazuh)
- Windows Event Logs
- Linux Logs
- Sysmon
- EDR
- Firewall Logs
- Proxy Logs
- Threat Intelligence

## Alert Investigation Questions

- Where did the alert originate?
- Which device is affected?
- Which user is involved?
- What time did it occur?
- Which detection rule triggered?
- What is the severity level?
- Is it expected activity?

---

## Gather Evidence

Evidence Sources

- SIEM logs (Wazuh)
- Endpoint logs
- Sysmon
- EDR
- VirusTotal
- AlienVault OTX
- User information
- Asset inventory

---

## Validate Alert

Determine whether the alert is:

- True Positive
- False Positive

False Positive Example

Employee entered the wrong password multiple times.

True Positive Example

Multiple failed logins from a foreign IP followed by a successful login.

---

# Incident Classification

Common Categories

- Malware Infection
- Phishing Attack
- Unauthorized Access
- Data Exfiltration
- Policy Violation

---

# 3. Containment

Purpose

Prevent the attack from spreading.

Typical Actions

- Disable compromised account
- Isolate endpoint using EDR
- Block malicious IP
- Block malicious domain
- Notify Incident Response Team

---

# 4. Eradication

Purpose

Remove the threat completely.

Typical Actions

- Remove malware
- Delete persistence mechanisms
- Patch vulnerabilities
- Reset passwords
- Remove malicious registry keys

Usually performed by L2/L3.

---

# 5. Recovery

Purpose

Restore systems safely.

Typical Actions

- Restore clean operating system
- Reconnect isolated endpoint
- Monitor for reinfection
- Validate business services

Recovery ensures systems are clean before returning to production.

---

# 6. Post-Incident Review

Purpose

Learn from every incident.

Activities

- Root Cause Analysis (RCA)
- Update detection rules
- Improve playbooks
- Share IOCs
- Create Lessons Learned report

# Important Terms

## Alert
Notification generated by a security tool.

## Event
A single occurrence recorded in logs.

## Incident
A confirmed security event requiring action.

## IOC
Indicator of Compromise such as:
- IP Address
- Domain
- URL
- File Hash

## RCA
Root Cause Analysis to identify how the attack happened.
